# FleetPro Dev Setup — Meeting Notes
*Date: 2026-08-16*

---

## Problem Statement

FleetPro (bounceops.online) is currently a single-person operation — all code changes, database changes, and deployments go through Vamsee directly. This creates a bottleneck:
- No developer can contribute safely without risking prod
- No staging environment to test changes before they go live
- GitHub and Supabase accounts are tied to a Bounce email, not Scalability Club
- No structured handoff process between developer, review, and deployment

---

## Solution

Set up a three-party development workflow with a proper staging environment:

1. **Manasa** writes and tests code on a staging site (bounceops.info)
2. **Claude Cowork** reviews PRs, applies DB migrations, orchestrates deployments
3. **Claude Code** executes git pushes with syntax checks
4. **Vamsee** is the final gatekeeper — reviews the PR diff, pastes one prompt, done

The live site (bounceops.online) is never touched until code is tested and approved.

---

## Activity List (in order)

### 🔴 Priority 0 — Ownership Transfer (do first, before anything else)

**Activity 1 — Transfer Supabase ownership**
- Create Supabase account under `vamsee@scalability.club`
- Go to current Supabase org → Settings → Members → Invite new account as Owner
- Accept invite on scalability account
- Remove Bounce email as owner
- ⏱ 10 mins | Risk: zero — project stays live throughout

**Activity 2 — Transfer GitHub ownership**
- Create GitHub account under `vamsee@scalability.club` (or use existing)
- Go to `github.com/vamseebounce/vehicle-parts-check` → Settings → Danger Zone → Transfer repository
- Transfer to the scalability account
- GitHub auto-redirects old URLs — bounceops.online unaffected (uses CNAME)
- ⏱ 10 mins | Risk: low — live site unaffected, just update remote URLs after

---

### 🟡 Priority 1 — Staging Environment

**Activity 3 — Create staging branch**
- `git checkout main && git pull`
- `git checkout -b staging && git push origin staging`
- ⏱ 2 mins

**Activity 4 — Set up branch protection rules on GitHub**
- `main` → require PR before merging, no direct push
- `staging` → Manasa can push directly or via feature branch PR
- ⏱ 5 mins

**Activity 5 — Set up Vercel for bounceops.info**
- Sign up at vercel.com
- New project → connect `vehicle-parts-check` repo → deploy branch = `staging`
- Add custom domain `bounceops.info`
- Update CNAME in domain registrar pointing to Vercel
- ⏱ 20 mins
- Advantage: Claude Cowork has Vercel MCP connected — can monitor staging deploys, check logs, and manage the domain directly without Vamsee logging into a dashboard

**Activity 6 — Invite Manasa to GitHub**
- Settings → Collaborators → Add her GitHub account with Write access
- ⏱ 2 mins

**Activity 7 — Supabase access for Manasa's Claude Code**
- No invite needed — the anon key is already in the repo (safe to share, public-facing)
- Her Claude Code uses the anon key to read tables, understand schema, write accurate migration `.sql` files
- Service role key (for migrations/deploys) stays only with Vamsee via Supabase MCP — she never needs it
- ⏱ 0 mins — already set up

---

### 🟢 Priority 2 — Manasa Onboarding

**Activity 8 — Manasa sets up locally**
- Install Claude Code on her machine
- Clone the repo
- Claude Code reads CLAUDE.md automatically — full project context on day one
- Reference: `docs/STAGING-SETUP.md` (already in repo)

**Activity 9 — Walkthrough of workflow**
- Show her the feature branch → staging → bounceops.info → PR flow
- Walk through the PR template (`.github/PULL_REQUEST_TEMPLATE.md`)
- Explain: she writes migration `.sql` files, never applies them herself
- Explain: she pushes feature branches, merges to staging herself, then opens PR to main

**Activity 10 — First test task**
- Give her a small, safe task (UI change, no DB)
- She goes through the full flow end-to-end
- Confirms bounceops.info deploys correctly
- Opens a staging→main PR — Vamsee pastes URL to Claude Cowork → push goes through

## How it looks after setup

```
Manasa writes code
       ↓
feature/xyz branch
       ↓ (she merges herself)
staging branch → auto-deploys → bounceops.info
       ↓ (she opens PR, fills template)
Vamsee glances at diff → pastes PR URL to Claude Cowork
       ↓
Claude Cowork: reads PR, applies migrations via MCP, writes push prompt
       ↓
Vamsee pastes prompt to Claude Code + fills <PAT>
       ↓
Claude Code: syntax checks JS → pushes to main
       ↓
bounceops.online updated ✅
```

---

## What Vamsee does per deployment
1. Read the PR diff — 2 minutes
2. Paste PR URL to Claude Cowork
3. Paste clipboard prompt to Claude Code + replace `<PAT>`

That's it.
